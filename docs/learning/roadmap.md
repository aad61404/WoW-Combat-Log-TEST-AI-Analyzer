# 全端、後端效能與 Cloud 學習計畫

更新：2026-10-20。狀態：能力驗收規則與第一份練習已建立；個人能力尚未驗收。

目標：獨立完成產品，並能以證據判斷系統是否承受指定負載、瓶頸在哪裡、改善的成本與限制。

## 來源與證據邊界

- 論壇討論：採用有限資源實驗、量測瓶頸、以成本和時間做取捨的方法。薪資、台灣市場與「九成人不懂」等說法不作學習規劃依據。
- Sky / Tom《從按下 k6 開始發現自己什麼都不懂》：依前次讀取的 45 頁文字與備註，採用使用者流程建模（p.11–16）、雙端監控（p.18–24）、業務成功（p.25–26）、瓶頸排查與實驗紀錄（p.31–44）。簡報內部數字是案例陳述，不是本專案實測或通用容量。
- 使用者貼上的另一份 AI 路線：作為待評估提案。
- `mobile-stress-test`：尚未取得並閱讀原始碼。在目前專案與相鄰專案目錄搜尋，未找到所述檔案。`scheduler/periodic.ts`、`loop.ts`、`bet-reason.ts`、`docs/har-api-analysis.md`、`docs/elk-error-review-20260415.md` 均待核對，不聲稱它們實作了任何特定機制。
- TypeScript、前端、狀態管理作為可利用的背景；熟練度由實作確認。貼文裡的研究所、AWS 經驗與 slot 專案不能直接視為使用者個人經歷。

## 對原提案的評估與修正

| 原建議 | 評估與本計畫決定 |
| --- | --- |
| 用自己的服務練壓測、觀測、成本 | 保留，是整條路線的核心。現有 WoW 專案已有前後端與離線 demo，可直接開始。 |
| 後端與 DB 從零，另建 Node slot 後端 | 不預設能力為零；已有 FastAPI 程式不代表使用者已熟悉。先做能力盤點。保留 Python 主線，TypeScript 用在前端與壓測；Node 小服務是可選延伸，不重寫主產品。 |
| SQLite 再換 PostgreSQL | 直接深入 PostgreSQL，避免為換工具而遷移。SQLite 可作比較閱讀。 |
| DB 是大多數瓶頸、快取做好就不崩 | 不能預設。CPU、外部 API、連線池、網路、壓測端也可能先飽和。先量測再決定是否使用 Redis。 |
| transaction 就能避免同帳號扣款錯誤 | 單純包 transaction 不足以保證業務不變量；還需原子條件更新、約束、適當鎖／隔離與衝突重試。主線改成重複分析工作的唯一性與冪等性實驗。[4] |
| 500 VU，每 10 秒一次＝50 RPS | 若每位使用者穩定每 10 秒啟動一次，平均目標是 50。若回應後 sleep(10)，還要加回應與其他工作時間；同步啟動也可能造成尖峰。arrival-rate 設的是 iteration 啟動率，一輪多請求不能當作相同 RPS。[2] |
| 能解釋為何一定是 65,535 條連線 | 改成理解 TCP 四元組、可用 ephemeral ports、連線重用與 NAT 限制。AWS NAT Gateway 每 IPv4 對唯一目的地約 55,000 同時連線；不是一個 IP 對所有目標的總上限。[1] |
| 不重用連線就一定重現 NAT port 耗盡 | 本機不一定經過 NAT，也可能先撞檔案描述符、CPU 或本機 port。先觀察連線生命週期，不把故障原因寫死。 |
| bcrypt 慢就快取登入 | bcrypt 是密碼雜湊驗證。先區分正常 session 驗證與每次登入的昂貴驗證；不可降低密碼安全性換數字。快取要設計登出、改密碼、停權與撤銷行為。 |
| TTL jitter、single-flight 都解快取雪崩 | TTL jitter 分散大量 key 同時到期；single-flight 合併同一 key 的並發重建。程序內合併不等於跨 worker 合併。 |
| label 只能固定少數值 | 原則是控制時間序列基數及其乘積，不是禁止所有動態值。使用路由模板、有限狀態；不用 user ID、token、report code、完整 URL 當 label。[3] |
| 只有異常才畫線 | 保留異常總覽，同時保留正常基線、流量與監控採集健康；無資料不能解讀為正常。 |
| 上雲一次用 EC2/ECS、RDS、Redis、ALB | 先做最小部署，依需求逐項加入。預算告警不是硬性支出上限；需資源清單、執行時限與刪除核對。 |
| 20 週完成、幾百人到幾萬人 | 20 週可作第一次循環，不保證精通或容量。以驗收調整時間；不追求漂亮但缺乏負載定義的人數。 |

## 專案基線與學習基線

2026-10-20 文件／程式檢視：已有 Next.js、FastAPI、離線 demo、分析引擎、WCL/Gemini 整合程式、pytest、Playwright 與 CI 設定。demo 路由確認不呼叫外部服務。

PostgreSQL、持久化歷史、正式部署與容量報告仍是待辦。真實 WCL/Gemini、遠端 CI 成功狀態不由這次文件修改認證；見 [live-validation](../live-validation.md)。本次未重跑應用測試。

本計畫是學習 backlog，不表示上述功能已實作；不改寫 [原產品規劃](../implementation_plan.md) 的版本承諾。先在隔離練習中驗證，再把適合產品的項目整合。

## 進度怎麼算

以 [能力驗收與進度](progress.md) 的 L1 解釋、L2 驗證、L3 診斷、L4 遷移與取捨衡量。
工具安裝與 AI 完成程式只記產出，不自動勾選個人能力。每個階段需附學習者證據與 AI 協助程度。
從 [練習 01：demo 流程與正確性](exercises/01-demo-flow.md) 開始。

## 時間與學習方式

暫以每週 6–8 小時安排：2 小時原理、3–4 小時實作、1 小時量測與紀錄、1 小時回顧。時間是估算；每階段以驗收通過為準。

AI 可以解釋、協助除錯與審查；學習者需要親自提出假設、改動程式、閱讀輸出並口頭解釋取捨。每階段完成適當檢查後 commit，公開內容不包含公司程式、HAR 憑證、內部位址或原始業務資料。

## M0：理解現有服務與網路（第 1–2 週）

- [ ] 畫出瀏覽器 → API → 正規化 → 分析 → 摘要的流程，指出純運算與外部 I/O。
- [ ] 補 Python 型別、例外、async/await；對照 TypeScript Promise；能說明 async 不等於 CPU 平行運算。
- [ ] 複習 HTTP method/status、Cookie/token、CORS、DNS、TCP、TLS、keep-alive、TIME_WAIT、HTTP/2 multiplexing。
- [ ] 用 DevTools Network 拆 demo 的 request、payload、response、Timing；HAR 僅保留去識別資料。
- [ ] Mac 用 `lsof -iTCP -n -P`／`netstat` 看連線；`ss` 留在 Linux VM 使用。
- [ ] 自己修一個小問題並補有意義的回歸驗證，解釋每一項改動。

驗收：不看 AI 回答也能追蹤一次請求、定位一個錯誤，解釋 port 數量為何不等於使用者容量。
交付：流程圖、API 表、能力缺口與修正 commit。

## M1：最小壓測與觀測基準（第 3–4 週）

- [ ] 學 k6 VU／arrival-rate、check／threshold、group/tag、iteration、p50/p95/p99、dropped iterations。
- [ ] 對本機 demo 做「讀報告 → 分析 → 檢查內容」，WCL/Gemini 使用 fixture/mock；不壓測第三方服務。
- [ ] 先 1 VU 驗證，再 5、10、20 VU 分段量測；每段例如 3 分鐘，依資源調整，不當成容量承諾。
- [ ] 檢查 HTTP 與業務結果：fight ID、已知死亡數、摘要來源；不可只看 200。
- [ ] 同時記錄 k6 與服務的 CPU、記憶體、實際 RPS、延遲、成功完成分析數；先用終端與結構化 log。
- [ ] 量測前寫門檻與停止條件，例如本機無法正常操作、持續錯誤或記憶體逼近預設界線；不以當機為目標。
- [ ] 記錄 commit、硬體、worker、資料集、暖機、重複次數；功能測試與效能測試分開執行。

驗收：能解釋 500 VU／10 秒例子的假設，能辨認「沒送出去」與「送出但失敗」。低樣本 p99 不做強結論。
交付：k6 腳本與第一份 [實驗報告](experiment-template.md)。同機結果只代表該拓撲，不宣稱為獨立 server 容量。

## M2：PostgreSQL 與完整產品流程（第 5–8 週）

- [ ] 學 SQL、JOIN、聚合、PK/FK/UNIQUE/CHECK、索引、交易隔離、鎖、migration、連線池。
- [ ] 設計 report、analysis job、result 的關係、版本與唯一性，明確定義何時可重用結果。
- [ ] 實作保存、歷史列表、分頁與可重新整理的結果 URL；學前端路由、載入／失敗／空資料狀態與基本可及性。
- [ ] 練習安全的參數化查詢；ORM 之外仍能解釋產生的 SQL。
- [ ] 定義冪等性範圍與有效期；相同請求並發 10 次，驗證只建立預期的一份工作／結果，或回傳明確衝突。
- [ ] 在隔離 DB 建合理合成資料，對照 EXPLAIN (ANALYZE, BUFFERS) 的查詢計畫、索引前後與寫入成本。
- [ ] 做一次 migration 與備份還原；驗證資料而不是只確認指令成功。

驗收：能解釋 transaction 為什麼不自動保證所有業務規則、如何避免重複工作；歷史結果可重訪。
交付：schema、migration、並發驗證、查詢比較與 UI 流程。

## M3：瓶頸與韌性實驗（第 9–13 週）

- [ ] 用合理的 1 千／1 萬／10 萬事件資料測 CPU、記憶體、分析耗時，保持已知正確結果。
- [ ] 分段量測 fetch、normalize、analyze、coach，profile 真正的熱點。
- [ ] mock 外部延遲、429、5xx、timeout；學 timeout budget、退避、jitter、重試上限及 Retry-After。
- [ ] 明確區分可重試讀取與可能重複副作用的操作；測試重試不會造成重複工作與流量放大。
- [ ] 比較連線池設定、連線重用；只有證據支持時才判定是哪一層耗盡。
- [ ] 若有重複分析瓶頸，再比較快取與 single-flight；設計 key（含版本）、TTL、失效與權限隔離。
- [ ] 若有長任務或 CPU 阻塞證據，再實驗獨立 worker／工作佇列，包含失敗、重啟、重複投遞與背壓。
- [ ] 一次只改一項，在相同負載／資料／資源下重跑；無提升也留下原因。

驗收：至少一個有量測證據的瓶頸、一個故障恢復案例。不能預先指定一定要撞到 NAT、快取雪崩或 DB。
交付：改善前後的延遲、成功吞吐、資源與正確性比較，不只寫「X 人變 Y 人」。

## M4：可觀測性、Linux 與部署（第 10–16 週，與 M3 部分並行）

- [ ] 學 process/thread、排程、記憶體、檔案描述符、I/O；在 Linux VM／現有設備練習，不要求先買硬體。
- [ ] 用 Docker Compose 建可重現服務；固定版本與資源設定，理解 Mac 容器仍經過 Linux VM。
- [ ] 用 Python 結構化 log 記 request ID、路由、耗時與錯誤分類；pino 僅在可選 Node 實驗使用。
- [ ] 加 Prometheus/Grafana：請求率、錯誤率、延遲分布、飽和度、k6 工作量；每張 panel 寫用途與下一個排查步驟。
- [ ] 學 PromQL、counter/rate、histogram；不可直接平均不同 instance 的 p95。
- [ ] 控制 label 基數，保留基線與監控自身健康；request ID 放 log，不當 metrics label。
- [ ] 學身分驗證與授權、secret 管理、HTTPS、反向代理、服務重啟、CI/CD 與回滾。
- [ ] 若開放外部存取，先驗證結果權限與昂貴分析的使用限制；CORS 不是授權機制。
- [ ] 演練部署失敗與 DB 還原；另機壓測若設備可用則做，否則註明同機干擾。

驗收：能從圖和 log 提出並驗證原因；重啟與回滾有步驟、還原後資料可用。
交付：部署／恢復 runbook、dashboard 與告警判讀說明。

## M5：Cloud 與成本（第 17–20 週，條件式）

進入條件：本機部署可重現、有基準實驗，已選帳號／區域與明確金額預算。這份計畫不建立付費資源。

- [ ] 學 IAM 最小權限、VPC/subnet、路由、安全群組、公開與私人存取、儲存與備份生命週期。
- [ ] 先估最小部署（例如單台 EC2）的方案；RDS、ALB、Redis、ECS 逐項說明需求後才加入。
- [ ] 設定預算告警、資源標籤、實驗時限與刪除清單；了解告警不等於自動停止計費。
- [ ] 查當時／當區域價格，估 compute、DB、磁碟、快照、流量、IPv4、NAT、LB、監控、外部 API 成本。
- [ ] 小量 fixture 壓測後對帳；分開一次性測試成本、實際期間費用與月費推估。
- [ ] 在相同延遲／錯誤／正確性條件下比較規格升級與程式優化，納入開發時間、維護與可用性需求。
- [ ] 結束後核對資源刪除與持續費用；不能用短時峰值線性外推全天容量。

驗收：說明「在指定工作負載和品質門檻下，成本估算是多少、哪些不確定」。不承諾免費額度或固定使用者數。
交付：成本表、架構圖、資源清理紀錄。

## M6：系統設計與職涯證據（第 21 週起持續）

- [ ] 從需求估算活躍行為、請求／工作率、資料量、尖峰與延遲目標，再選架構。
- [ ] 學 cache、queue、replica、partition、CDN 的一致性、失敗與操作成本；不只為吞吐擴展，也考量可用性與隔離。
- [ ] 先用模組化單體解題；依實際限制論證是否需要分散式。
- [ ] 穿插資料結構、複雜度、OS、網路與 DB 原理；刷題依求職時間平行安排。
- [ ] DDIA 對照實驗主題閱讀；CMU 15-445、MIT 6.5840 作進階選修，開課版本、先備知識與實驗要求屆時核對，不當作本期硬性清單。
- [ ] 整理作品：正確性案例、效能報告、故障恢復、成本比較與設計取捨。

驗收：能提出方案，也能解釋為何暫時不需要某個元件；無需以幾萬 VU 作畢業門檻。
